# SPEC — Учёт оргтехники: доступ по партиям (изменение)

**Дата:** 2026-09-15 · **Статус:** на согласовании
**Основа:** существующее приложение (app.py, Streamlit + SQLAlchemy). Контекст проекта —
DEV-JOURNAL.md. Это доработка работающей системы, а не новый проект.

## 1. Зачем

Сейчас инженер сам выбирает любую из 31 партии из списка и сам печатает своё ФИО.
Поэтому он может смотреть, править и удалять позиции чужой партии, а в журнале стоит
имя, вписанное руками (доказать авторство нельзя). В партиях люди меняются каждый месяц.

**Задача:** в чужую партию попасть нельзя, а каждая операция подписана реально
подтверждённой фамилией того, кто работает.

## 2. Как будет (схема пользователя)

1. **Вход:** режим «Инженер» → выбор партии → **пароль партии**.
2. **Кабинет партии:** верный пароль → появляется окно подтверждения фамилии:
   «Вы — <ФИО>?» → **[Подтвердить]** или **[Сменить]** (список: инженеры, уже работавшие
   в этой партии + ввод другой фамилии).
3. **Работа без вопросов:** список, добавить, переместить, править.
4. **Уточнение фамилии — один раз в сутки:** первая операция нового дня спрашивает
   «сегодня работает <ФИО>? подтвердить/сменить», дальше до конца суток не спрашивает.
5. **Пароль запоминается в браузере** (подписанная ссылка-токен вместо пароля в адресной
   строке): на телефоне не нужно вводить пароль после каждого обновления страницы.
   Streamlit сбрасывает состояние при F5 — без этого вход пришлось бы повторять.
6. **Пароли партий хранятся в БД** (хэш, не открытый текст), задаёт и меняет
   администратор во вкладке «Партии». Админский режим остаётся на своём пароле (secrets).

## 3. Права

| Действие | Инженер (в своей партии) | Администратор |
|---|---|---|
| Смотреть список партии | да | все партии |
| Добавить / переместить / исправить позицию | да | да |
| Удалить безвозвратно | **нет** | да |
| Списать в архив | да (с отметкой кто/когда) | да |
| Вопросы паролей партий | нет | да |
| Сводка, дашборд, журнал, Excel | нет | да |

## 4. Что НЕ трогаем (рабочие места, которые нельзя ломать)

Лимиты (ноутбуки ≤2, сетевые фильтры ≤2, остальное ≤1), категории, сводку, дашборд,
QR-коды и печать наклеек, перемещения и их проверки фамилий, Excel-выгрузки, работу
админской вкладки «История». Локальную SQLite и файл секретов.

## 5. Критерий приёмки (как проверим, что «работает»)

1. Неверный пароль партии — в кабинет не пускает.
2. В кабинете видны и правятся **только** позиции этой партии.
3. Добавление/правка требует подтверждения фамилии; после подтверждения в тот же день
   операции идут без вопросов.
4. На следующий день первая операция снова просит подтвердить фамилию.
5. Все операции в журнале подписаны подтверждённой фамилией и партией.
6. Инженер не может удалить позицию безвозвратно — только списать в архив.
7. Обновление страницы (F5) не выкидывает из кабинета и не просит пароль заново.
8. Старые данные на месте: SQLite-база и Postgres открываются, миграция не теряет строк.

## 6. Данные (только новое)

- `party_access { party, password_hash, updated_at }` — пароль каждой партии.
- `party_session { party, fio, confirmed_date, confirmed_at, archived_flag }` — кто когда
  подтверждал фамилию (он же — источник списка «инженеры, работавшие в партии»).
- `Equipment.archived`, `archived_at`, `archived_by` — мягкое удаление вместо стирания.
- Миграция — в стиле `migrate_history_schema()` (ALTER TABLE ADD COLUMN, без потери данных).

## 7. Честно про границы защиты

Пароль партии знают все её инженеры. Если кто-то передаст пароль человеку из другой
партии, тот войдёт — но это будет видно в журнале: подтверждённая фамилия, партия, время.
Полная защита — личные коды каждому инженеру; схема это не блокирует: `party_session.fio`
и место пароля партии в БД позволяют позже заменить пароль партии на личный код без
переделки логики.
